# CTX-306.3: Already-Saved Detection

> **Spec Reference:** Links to [SPEC-306](../specs/SPEC-306-component-discovery.md)

## 1. Feature Definition & Execution Plan

Real, connected UX gap reported directly by the user, distinct from `CTX-315.4`'s own "reopen a
saved Part from the Library" fix and `CTX-306.2`'s own "don't lose in-progress work on a tab switch"
fix -- both already shipped, neither actually solved this: **"Save to Library" is still a gatekeeper
to the rest of Part Detail even when the part is already saved.** A user re-discovering a part
through Components search (not the Library browser) still had to click "Save to Library" again
before Design Requirements, footprint export, or anything else unlocked -- regardless of whether a
real Part with that exact `part_number` already existed. Connected to a second real gap: search
results carried no indication a candidate was already saved, so a user re-searching for something
they'd already confirmed couldn't tell at a glance, and "may just want to revisit the component in
their library" (the user's own words) had no faster path than re-confirming from scratch.

**Root cause, confirmed by reading the real code**: `PartDetail`'s own extraction effect, when
entered via a fresh `candidate` (`ComponentDiscovery`'s search/confirm flow, `SPEC-306`'s own
territory), unconditionally ran `extractPartDetail` (a real SPEC-202 LLM re-extraction) with zero
awareness a Part with that `part_number` might already be saved -- `savedPart`/`savedSymbol` only
ever got populated by a fresh `handleSave` click. `CTX-315.4` built the exact hydration machinery
this needed (`initialPartToExtraction`/`initialPartToSymbol`, the `initialPart` entry point) but only
wired it to the Library-browser entry point, not to a `candidate` that turns out to already be saved.

**Fix, part one (`PartDetail.tsx`, `SPEC-307`'s own territory)**: before running real extraction, the
effect now tries `loadPart(candidate.part_number)` first. A real, already-saved record hydrates
`extraction`/`savedPart`/`savedSymbol` exactly like the `initialPart` path (same two helper
functions, same shape) and extraction is skipped entirely -- "Save to Library" never renders, since
its own gate (`!savedSymbol`) is already false. A `loadPart` failure is the expected, common case for
a genuinely new part (not a real error) and falls through to the original extraction flow, unchanged.

**Fix, part two (`ComponentDiscovery.tsx`, this spec's own territory)**: after a real search returns
results, a real, fast local lookup (`library.list_parts`, already-existing, already used by
`LibraryArea`, no backend change needed) fetches every currently-saved `part_id`. Each candidate
already in that set gets a real "Already in your library" badge and, when the app provides
`onOpenSavedPart` (wired in `App.tsx` to the same `partDetail` view `CTX-315.4`'s own Library-row
click already opens -- not a second, parallel navigation path), a direct "Open" shortcut that skips
confirm/extract entirely.

### Phase 1: `PartDetail.tsx`
*   [x] The extraction effect tries `loadPart(candidate.part_number)` before `extractPartDetail`;
    success hydrates directly (reusing `initialPartToExtraction`/`initialPartToSymbol`) and skips
    extraction; failure falls through to the original flow unchanged.

### Phase 2: `ComponentDiscovery.tsx`
*   [x] New optional `onOpenSavedPart?: (partId: string) => void` prop.
*   [x] `handleSearch` fetches `listParts()` after a successful search (best-effort -- a failure here
    only means no badges render, not a search error) and stores the result as a real `Set<string>`.
*   [x] Each candidate already in that set renders an "Already in your library" badge and, when
    `onOpenSavedPart` is provided, a real "Open" button alongside "This one".

### Phase 3: `App.tsx`
*   [x] `ComponentDiscovery` now receives `onOpenSavedPart={(partId) => setView({ kind: 'partDetail', partId })}`.

### Phase 4: tests
*   [x] `PartDetail.test.tsx`: a real, already-saved candidate hydrates directly, never calls
    `extractPartDetail`, never shows "Save to Library"; a genuinely new candidate still runs real
    extraction. **Found and fixed a real test-infrastructure gap while writing these**: the existing
    mock for `../lib/partDetail` didn't define `loadPart` at all, so every pre-existing test's own
    call to the new `loadPart` inside the effect silently threw (caught by this fix's own
    not-found-is-expected `catch`), accidentally falling through to the old extraction path for the
    *wrong* reason (an unmocked function, not a deliberate "not found"). Added a real `loadPartMock`
    with an explicit rejecting default so every existing test exercises the real fallback path on
    purpose.
*   [x] `ComponentDiscovery.test.tsx`: an already-saved result shows the badge and Open button, and
    clicking Open calls `onOpenSavedPart` with the real `part_id`; a not-yet-saved result shows
    neither; without `onOpenSavedPart` provided, the badge still shows but no Open button renders.

None from either spec's own original design -- this closes a real gap `CTX-315.4` left open (it
solved reopening from the Library browser, not the search/confirm path), applying the exact same

inventing a second mechanism. `PartDetail.tsx`'s own change lives in `SPEC-307`'s file but is
recorded here (not split into a separate `SPEC-307` context) since both halves are one connected fix
for one connected, real user report, found and shipped together.
